## M2 — MEDIUM — the edit-history panel diffs every version, with no cap (OWNER DECISION)

- Touches: the "Earlier versions" panel on any post card
  (`renderEditHistoryPanel`, public/js/render.js:710-733) and
  `GET /api/posts/:id/edits` (api/posts-write.mjs:430).
- Threat: before v5.50 each past version was one `textContent` write. Now
  every version is word-diffed against the one before it
  (`versions.forEach` at render.js:719, `editDiffBody` at :704). One diff is
  an O(n·m) LCS table, bounded at `DIFF_MAX_WORDS` (2000) words per side;
  the worst case at the cap measured about 70 ms on a desktop. The edits
  route returns every stored version with no LIMIT, so the panel's cost is
  that worst case times the number of edits, all on the main thread.
- Failure scenario: an author edits one post many times, swapping between
  two unrelated bodies of about 2000 one-letter words (inside the body
  cap). Each edit passes the post-write limiter. After 100 such edits,
  anyone who opens that post's edit history freezes their tab for several
  seconds (longer on a phone). Nothing is exposed and nothing is written;
  the viewer has to click to trigger it and a reload recovers.
- Recommendation (pick one): (a) diff only the newest N versions (say 10)
  and show the rest plain; (b) a total cell budget across the panel, falling
  back to plain text once spent; (c) diff a version only when its row is
  opened. Separately, a hard LIMIT on the edits SELECT would bound the
  payload. No schema change for any of these.
- Not pinned with a `todo`: the right fix shape is the owner's call, and a
  timing-based `todo` would be flaky. The existing timing pin in
  tests/wave550-word-diff.test.mjs bounds one diff only.

## L2 — LOW — a lock on a thread deleted mid-request answers 500 (OPEN)

- Touches: `PUT /api/admin/threads/:id/lock` (staff only).
- Threat: `lockThread` (api/thread-locks.mjs:90-96) checks the root with
  `rootThread` and then runs `LOCK_UPSERT_SQL` (:47-49), a plain
  `INSERT ... VALUES`. If the author deletes the thread between the two
  statements, the INSERT fails the `post_id` foreign key and the error is
  not caught, so the route answers 500. The TL;DR upsert avoids this with
  `INSERT ... SELECT ... WHERE EXISTS` (api/thread-summaries.mjs:52-55).
- Failure scenario: a staff member locks a thread at the moment its author
  deletes it. They see a generic failure and the worker log gets one
  "Forum request failed" line. Nothing is written, nothing is exposed, and
  only staff can reach the route.
- Recommendation: give the upsert the same `WHERE EXISTS (... parent_id IS
  NULL)` guard and answer 404 when `meta.changes` is 0. No schema change.

## O8 — LOW — what a lock stops (OWNER DECISION)

- Where: api/thread-locks.mjs. The lock refuses new replies only, on both
  reply paths. Members can still edit and delete their existing posts in
  the thread, react, vote in its poll, and the thread's author can still
  change or remove its TL;DR. tests/wave551-thread-lock.test.mjs pins
  edits and reactions as allowed.
- Why it is a question: staff often lock a thread to stop a heated
  exchange. An author could still rewrite the root body or the TL;DR (both
  word-filtered and kept in the public edit history) after the lock.
- Options: (a) keep (replies only); (b) also refuse edits and TL;DR
  changes by non-staff while locked (one more `assertThreadUnlocked` call
  each); (c) refuse edits only.

## O9 — LOW — no lasting record of a lock (OWNER DECISION)

- Where: `unlockThread` (api/thread-locks.mjs:99-103) deletes the row, so
  nothing records who unlocked a thread or when. Migration 0075 cascades
  `locked_by`, so deleting a staff account quietly unlocks every thread it
  locked (pinned in wave 5.51). The export has no lock section, so a staff
  member's own lock reasons are not in their "Download my data" file
  (pinned in this wave).
- Why it is a question: the module notes say the row is the record because
  there is no shared mod-log helper; once the row is gone the record is
  gone.
- Options: (a) keep; (b) write lock/unlock lines to the mod log
  (`api/modlogs.mjs`) without the member-facing reason; (c) add a
  `threadLocks` export section for the locker (post id, reason, time).
  Changing the cascade to SET NULL would need a table rebuild, which the
  migration law forbids, so a fix would keep locks through a re-lock
  instead.

## A9 — LOW — a TL;DR written by staff follows the writer, not the thread (ACCEPTED)

- `summarySelectSql` (api/thread-summaries.mjs:47-49) applies the ban and
  block filters to `updated_by`, and migration 0074 cascades `updated_by`.
  So a summary staff wrote on a member's thread disappears for a viewer who
  blocks that staff member, while the member is banned, or for everyone
  once that staff account is deleted. The thread's author can also
  overwrite or remove it.
- Accepted: it treats the summary as the writer's own text, like a reply,
  which is the visibility law's rule. The author can always write a new
  one.

## Checks that passed

- **TL;DR route authz and order.** GET: id `[0-9]{1,15}`, optional session,
  `postById` + `canViewPost`, roots only. Missing, hidden, banned-author,
  block-paired (both ways) and reply ids all answer the same 404 body
  (pinned in this wave). PUT/DELETE: `requireUser` (same origin + CSRF),
  `assertNotBanned`, the write limiter, then `canViewPost` (404), roots
  only (400), author or staff only (403); a 403 is reachable only on a
  thread the caller can already see (api/thread-summaries.mjs:107-133).
  Pinned in wave 5.50.
- **TL;DR binds.** `summarySelectSql` binds the post id and the staff flag,
  plus the viewer id twice only when `viewerBlockFilterSql` adds its clause
  (a signed-in non-staff viewer). The caller's condition
  (`viewer && viewer.id && !staffFlag`, :92-96) matches the vendor helper's
  (`!viewer || !viewer.id` or a staff role means no clause), so the
  placeholders always equal the binds: guest 2, staff 2, member 4, with
  `LIMIT 1`. Pinned in this wave by capturing the real statement.
- **TL;DR write.** The upsert re-checks the root inside the INSERT
  (`WHERE EXISTS`, :52-55) and a 0-row result is a 404, so a thread deleted
  mid-request writes nothing. DELETE is idempotent and keyed on the post.
- **Text rules.** `summaryBody` and `lockReason` trim, count code points
  (the same unit as SQLite's `length()` once NUL is refused), and refuse
  C0 (NUL, tab, line breaks), DEL, C1, U+2028/2029 and the bidi
  embedding/override/isolate controls through the one shared
  `isRefusedChar` (:66-68); U+200E/200F stay allowed. The TL;DR is public
  text, so a word-filter change refuses it (400) instead of masking into
  storage; `ensureFilterWords` primes the list at the top of every API
  request, so `filterWords(env)` is never cold. The lock reason is
  staff-only text and is not word-filtered. Parity pinned in this wave
  across U+0000-U+3000.
- **Lock route authz.** GET: `requireStaff(…, false)` (anon 401, member
  403). PUT/DELETE: `requireStaff` (same origin + CSRF), `assertNotBanned`,
  the write limiter; PUT roots only (400) and 404 for a missing thread;
  DELETE of an unlocked thread 409 (`meta.changes`). Staff-only 404/400/409
  are not oracles. Pinned in wave 5.51.
- **423 vs 400 vs 404.** Both reply paths run the target, depth and
  `canViewPost` checks first and the lock check after
  (api/replies.mjs:127-161, api/mcp.mjs:606-635), so a hidden,
  banned-author or block-paired thread answers the same 400 locked or not,
  on the web and over MCP (pinned in this wave). The `locked` flag itself
  is public on any thread the viewer can see, so the 423 tells nothing new.
- **Lock enforcement.** One primary-key lookup with one bound id on the
  resolved root (`bumpTargetId`, the parent for a level-2 reply), staff
  exempt with no query; members (including the thread's author) get 423 +
  `thread_locked` and nothing is written. Pinned in wave 5.51 for both
  depths and both paths.
- **POST_SELECT `locked`.** A bind-free `EXISTS` on the primary key
  (api/core/shapers.mjs:58); `publicPost` serves only a boolean (:266). The
  reason and the locker are read only by the desk GET (`LOCK_READ_SQL`,
  api/thread-locks.mjs:50-52); the refusal body, the thread, its replies,
  the feed and the export never carry them (pinned in waves 5.51 and 5.53).
  POST_SELECT's bind count stays 1.
- **Export contents.** `threadSummaries` reads `WHERE updated_by = ?`
  (summaries the caller wrote, on their own threads or, for staff, others'),
  capped at 2000 (api/export.mjs:134-136). A summary staff wrote on the
  caller's thread stays out. Pinned in wave 5.50.
- **Migrations 0074-0075.** CREATE TABLE / CREATE INDEX IF NOT EXISTS
  only; every user and post reference is `ON DELETE CASCADE`; CHECKs mirror
  the route caps (1-280, NULL or 1-200); child-side indexes exist for the
  writer and locker cascades. Pinned in waves 5.50 and 5.51.
- **Word diff DOM safety.** `appendWordDiff` builds text nodes and
  `<ins>`/`<del>` through `createElement` + `textContent` only; no
  `innerHTML`-family sink, `document.write`, `eval` or `window.open` was
  added anywhere in the range. Pinned in wave 5.50.
- **Spoilers in the diff.** Both sides go through `maskSpoilers` before
  `diffWords` (render.js:704-708), and the plain fallback masks too, so a
  spoiler never shows on either side. The TL;DR box masks its text
  (`maskSpoilers` into `textContent`); the editor prefills the raw text
  only for the author and staff. Pinned in wave 5.50; the spoiler sweep is
  green with no new allow-list entry.
- **Diff bound.** Common prefix and suffix are trimmed first; either side
  over `DIFF_MAX_WORDS` returns null and the row falls back to the plain
  full text; the `Uint16Array` table cannot overflow at 2000. One diff is
  bounded (pinned in wave 5.50); the number of diffs per panel is M2.
- **Client lock UI.** The note, staff reason line and composer gate build
  with `createElement`/`textContent`; the reason line is shown only to
  staff and fetched from the desk route; `stripReplyControls` spreads the
  NodeList before removing; the lock path accepts only a positive integer
  id. The server enforces everything the client hides. `window.prompt` is
  staff-only and its value goes through `lockReason`. Pinned in wave 5.51.
- **Device storage.** thread-summary.js, thread-lock.js and word-diff.js
  touch no `localStorage`/`sessionStorage`; no new key family, so the
  logout wipe needs nothing new.
