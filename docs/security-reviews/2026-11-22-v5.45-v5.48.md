## L1 — LOW — text that starts with U+0000 answers 500 instead of 400 (OPEN)

- Touches: `PUT /api/users/:username/note` (body) and
  `POST /api/me/saved-searches` (name and q).
- Threat: `noteBody` (api/private-notes.mjs:68-76), `savedName` and
  `savedQuery` (api/saved-searches.mjs:70-88) check the trimmed length in
  JavaScript, where U+0000 counts as one character and `trim()` keeps it.
  SQLite's `length()` stops at the first NUL, so the table CHECKs
  (`length(body) BETWEEN 1 AND 280`, `length(name) BETWEEN 1 AND 40`,
  `length(q) BETWEEN 1 AND 100`) see 0 and refuse the row. The constraint
  error is not caught and the route answers 500.
- Failure scenario: a script sends `{"body":"\u0000hi"}`. The member gets a
  500 and a "Forum request failed" line lands in the worker log for each
  try. Nothing is written, nothing is exposed, and only the caller's own
  request fails; the write limiter caps the log noise. The browser forms
  cannot normally produce a NUL.
- Recommendation: refuse U+0000 (or all C0 controls except tab/newline) in
  the three validators with a 400, before the INSERT. No schema change.
- Pinned (tests/wave549-security-review.test.mjs): a `todo` test sends all
  three shapes and expects 400; it fails today and turns green with the fix.

## A5 — LOW — thread mutes have no per-member cap (ACCEPTED)

- `MUTE_INSERT_SQL` (api/thread-mutes.mjs:36-37) has no count guard, unlike
  notes and saved searches.
- Accepted: a mute needs a thread root the member can see, so rows are
  bounded by the number of visible roots; every PUT runs the write limiter;
  the primary key makes repeats free; the detail read is one PK probe.

## A6 — LOW — a mute on a thread that is later hidden cannot be removed until it is visible again (ACCEPTED)

- `muteGate` (api/thread-mutes.mjs:51-64) runs `canViewPost` for DELETE as
  well as PUT, so a hidden, banned-author or block-paired thread answers 404
  to an unmute.
- Accepted: the 404 is the visibility law's (no oracle), a hidden thread
  sends no notifications anyway, the row is the member's own, and it goes
  with the thread or the account (cascade).

## A7 — LOW — a member's private notes about someone vanish when that someone deletes their account (ACCEPTED)

- `private_notes.subject_id` cascades (migrations/0072_private_notes.sql).
- Accepted: the note is about a person who has left; the profile it hung
  from is gone too. Pinned in wave 5.47.

## Checks that passed

- **Mute route authz.** `requireUser` (same origin + CSRF), `assertNotBanned`,
  the write limiter, then `canViewPost` — missing, hidden, banned-author and
  block-paired (both ways) threads all 404 with the same body (pinned in this
  wave); replies 400; ids `[0-9]{1,15}`; both directions idempotent
  (api/thread-mutes.mjs:51-77). Pinned in wave 5.46.
- **Mute predicate.** `mutedThreadSql` (api/notifications.mjs:65-69) resolves
  the root as `COALESCE(grandparent, parent, self)` from the row's
  `reply_id`, correct for roots, level-1 and level-2 replies (replies go two
  levels deep at most); a NULL `reply_id` matches no post, so label-only rows
  (chat mentions, invite joins, appeal outcomes) never mute. Pinned in this
  wave against the real schema.
- **Every fan-out.** All post-scoped notification INSERTs go through
  `insertNotificationSql` (api/notifications.mjs:84-88: reply, subscription,
  mention, web and MCP) or the follower fan-out (api/follows.mjs:69-77); both
  carry the predicate. `notifyStatement` is label-only and correctly does
  not. Pinned in wave 5.46 (web reply, sub-reply, subscription, mention, MCP,
  follow_thread, lobby mention).
- **Notification binds.** 9 unlabelled / 10 labelled per INSERT, 5 in the
  follower fan-out (the predicate keys on columns there); all far under
  `D1_MAX_BOUND_PARAMS`. Pinned in wave 5.46.
- **viewerMuted.** Only on a root's detail read and only for a signed-in
  viewer, one PK probe on the viewer's own row (api/posts-feed.mjs:565-569);
  never in feeds, other members' payloads or guest reads.
- **Private notes: owner only.** Every statement keys on the session's own
  id (api/private-notes.mjs:39-49); the subject, other members, staff (no
  bypass) and guests read only their own (empty) note. GET is a signed-in
  read; PUT/DELETE are CSRF + write limited; PUT is refused for a banned
  owner. Unknown member 404, self 400 (and a table CHECK). Pinned in wave
  5.47.
- **Private notes: cap race.** The 1000-subject cap is inside the upsert's
  `INSERT … SELECT … WHERE (SELECT COUNT(*) …) < 1000`; an edit at the cap
  falls back to an UPDATE of the existing row only (api/private-notes.mjs:
  43-46, :82-95).
- **Saved searches: owner only.** List, insert and delete all key on the
  session's id; DELETE of another member's id answers the same 404 body as an
  unknown or malformed id (pinned in this wave); staff have no bypass.
  POST is CSRF + write limited + not banned (api/saved-searches.mjs:146-160).
- **Saved searches: validation and cap.** q uses the search route's own
  `SEARCH_QUERY_MAX_CHARS` on the lowercased text; `in` must be one of
  `SEARCH_IN_SCOPES`; `by` must pass `isValidUsername`; name 1-40. The
  20-row cap and the duplicate name (NOCASE UNIQUE) are enforced inside the
  INSERT, and the list has `LIMIT 20` (api/saved-searches.mjs:44-57). The
  module runs no search.
- **search.mjs swap.** `SEARCH_QUERY_MAX_CHARS` (100) and `SEARCH_IN_SCOPES`
  replace the literals one for one; the same 400s are pinned in wave 5.48.
- **Unicode lengths.** The JavaScript checks count UTF-16 units, which is
  never fewer than SQLite's code points, so an over-long astral note or name
  is a 400 before the CHECK (pinned in this wave: 140 emoji note OK, 141
  refused; 20 emoji name OK, 21 refused). The only gap is L1 (NUL).
- **Export contents.** `privateNotes` reads `WHERE n.owner_id = ?` (notes
  the caller wrote; notes about the caller stay out) and `savedSearches`
  `WHERE owner_id = ?`, each capped (api/export.mjs:123-130). Pinned in
  waves 5.47 and 5.48.
- **Migrations 0071-0073.** CREATE TABLE / CREATE INDEX IF NOT EXISTS only;
  every user and post reference is `ON DELETE CASCADE`; CHECKs mirror the
  route caps; child-side indexes exist for the cascades. Pinned in waves
  5.46-5.48.
- **Client sinks and links.** No `innerHTML`-family sink, `document.write`,
  `eval` or `window.open` added. Note text lands through `textarea.value`;
  saved-search names, queries and outline authors through `textContent`;
  run links are built with the URL API onto the existing search page
  (public/js/saved-searches.js:41-46); the outline looks up cards by a
  numeric id. A failed note or saved-search load removes the box rather than
  offering an editor over unloaded data.
- **Device storage.** The only new key family is
  `forum-thread-outline:u<id>`, written only once the account id is known
  and wiped by `clearAllThreadOutline` in `wipeAccountLocalData`
  (public/js/routes/account-nav.js:283). Notes and saved searches store
  nothing on the device. Pinned in wave 5.46 and by the storage-wipe sweep.
