## L1 — LOW — the invite claim went out without a CSRF token (FIXED)

- Where: `prepareRouteContext` called `claimPendingInvite(api)` (a
  `POST /api/me/invite`) BEFORE `setCsrfToken(session.csrfToken)`
  (public/js/app.js:177 vs :183 before the fix). `api()` adds
  `X-CSRF-Token` only when a token is stored (public/js/api.js:52).
- Trust boundary: none crossed. The server gate held: `requireUser` demands
  same-origin + `X-CSRF-Token` (api/invites.mjs:79, api/core/auth.mjs:229),
  so the token-less POST got a 403.
- Failure scenario: the main invite path is /join?ref=X (signed out) → Wempo
  Accounts sign-up → a full page load back on the forum. On that load no
  token is stored yet, the claim is refused, and the ref has already been
  forgotten (invite.js clears it before the request), so the invite is never
  credited. It fails closed: a broken feature, not an exposure. (The signed-in
  /join path worked, because its claim runs after the context is prepared.)
- Fix: the token is stored right after the session read, before the claim
  (public/js/app.js:177). Nothing else changes; the token is the same one the
  old code stored a few lines later.
- Pinned (tests/wave537-security-review.test.mjs): a source pin keeps
  `setCsrfToken(session.csrfToken)` ahead of `claimPendingInvite(api)` in
  `prepareRouteContext`, and a route test shows a claim without
  `X-CSRF-Token` is a 403 with no row.

## O2 — LOW — the data export leaves out the member's invite record (OWNER DECISION)

- Where: `SECTION_READERS` (api/export.mjs:97-112) exports posts, bookmarks,
  followed threads, own blocks, wall posts and authored DMs. Migration 0064
  added one row per claimant (`invites`: inviter, claimed at) that the export
  does not include, in either direction.
- Why it is not a defect today: the export's written scope is "what THEY
  wrote and set" (api/export.mjs:20-37), and reactions and poll votes are left
  out under the same rule. The row is never public, both columns cascade on
  account deletion (migration 0064, pinned in wave 5.34), and the member sees
  the inviter on the welcome card while it shows.
- Failure scenario: after the 7-day welcome window a member has no way to see
  that the forum records who invited them, and the download that is meant to
  show their data does not mention it.
- Options (an export format change, so not made here): (a) add an `invitedBy`
  section (inviter username + claimed at; the read-time ban/block filter of
  `invitedBy()` decides whether the name shows); (b) also list whom the member
  invited (usernames only); (c) keep the current scope and say so in the
  privacy text.

## A1 — LOW — feeds and /week are unmetered public reads (ACCEPTED)

- `/feed.xml` and `/c/<board>/feed.xml` cost two D1 reads per request (the
  feed query with its per-row reply count, plus branding) and a SHA-256 of
  the document, even when the `If-None-Match` matches: the ETag is computed
  over the bytes (api/feeds.mjs:79-87). The `s-maxage` header does not put a
  Worker response in Cloudflare's cache by itself, so feed readers polling
  every minute all reach D1. `/api/week` computes the visible reply tally for
  every public root of the last 7 days before it sorts and cuts to
  `FEED_PAGE_SIZE` (api/week.mjs:50-67).
- Accepted: every statement is bound, indexed and `LIMIT`ed; reads do not
  touch the write quota; the anonymous feed, `/api/posts` and the sitemap
  already have the same shape. It sits with O1 and the wave 5.33 A1: page and
  feed loads are the unmetered paths. If the owner picks O1 option (a), the
  same keyed limiter can gate feeds.

## A2 — LOW — a lured /join link credits whoever's link was opened first (ACCEPTED)

- A signed-in account younger than 7 days with no invite row that opens
  `/join?ref=<anyone>` claims that ref at once (public/js/app.js:225-233): the
  claim is a same-origin POST with the CSRF token, so it is the member's own
  navigation, not CSRF. The first eligible claim wins and cannot be changed.
- Effect: the inviter sees one bell row naming the new member, and the new
  member sees "Invited by @user" on their welcome card. Nothing is public, the
  bell row and the welcome line drop while either side is banned or
  block-paired (api/notifications.mjs:96-98, api/invites.mjs:62-64), and
  blocking the inviter removes both. Accepted as the feature's design: the
  credit goes to the link the member arrived on.

## A3 — LOW — "Newest members" names accounts that never posted (ACCEPTED)

- `/api/members/newest` lists the 5 newest accounts to anyone, including
  accounts with no public post (which the sitemap does not list), with no
  opt-out (api/newcomers.mjs:35-50).
- Accepted: it adds no data that is not already public. Every profile is
  readable by name and already shows `joinedAt` (api/profiles.mjs:123); the
  route itself sends only the username and avatar URL, never the join time;
  actively banned members are never listed and block pairs are dropped both
  ways (binds 0 or 2). It is an owner-ordered welcome feature (v5.35).

## Checks that passed

- **Feed XML escaping.** Every value goes through `xmlText`: the five XML
  entities, then removal of the characters XML 1.0 forbids (C0 controls but
  tab/LF/CR, U+FFFE/FFFF; api/feeds.mjs:56-59). Element text and the one
  attribute (`atom:link href`) are both covered; no CDATA is emitted, so a
  `]]>` in member text is just escaped text. A lone surrogate is written as
  U+FFFD by the UTF-8 encoder. Pinned in wave 5.34 (breakout, forbidden
  characters).
- **Feed visibility and spoilers.** The feed is discovery's anonymous public
  root SQL (`visibility = 'public'` + `banFilterSql`, roots only,
  `FEED_PAGE_SIZE`, no caller limit; api/discovery.mjs:72-73, :105-110).
  Titles (`titleOf`) and descriptions mask spoilers before the cut. Pinned in
  wave 5.34.
- **Feed cache, ETag and CORS.** The feed never reads a cookie, so one
  document serves everyone; `Access-Control-Allow-Origin: *` sits only on the
  feeds and llms.txt (api/feeds.mjs:64-70), which carry public data and no
  `Set-Cookie`. `If-None-Match` is split on commas and compared exactly; `*`
  answers 304; HEAD gets headers only. Pinned here: a blocking member gets the
  byte-identical feed and ETag a guest gets, and `/api/session` has no
  wildcard CORS.
- **Board allowlist.** `^/c/([a-z0-9-]+)/feed\.xml$`, then
  `BOARD_VALUES.includes` (api/feeds.mjs:57, :164); unknown boards 404 before
  any read; the board is a bound parameter.
- **llms.txt.** Static: branding name and tagline (staff-set) as plain text,
  the fixed board list and fixed links; it never reads a post or a member.
  Pinned in wave 5.34.
- **Head feed links and the /week head.** Feed `<link rel="alternate">` title
  and href go through `attributeEscape`; the board is from the router's
  allowlisted route. The /week head is fixed text plus the branding name.
  Both insertions ride the v5.33 function replacement (api/seo.mjs:255,
  worker.mjs:170), pinned in wave 5.33.
- **v5.33 M1 fix and the AutoMod doc.** Reviewed in the previous review;
  unchanged here.
- **Invite claim race.** `user_id` is the primary key; `INSERT OR IGNORE`
  then `meta.changes !== 1` returns `inviter: null` with no bell row
  (api/invites.mjs:60, :89-91), so two parallel claims give one row and one
  ping. The eligibility read also refuses when a row exists.
- **Invite eligibility.** Claimant inside the 7-day window, ref an existing
  member who is not the claimant, joined no later than the claimant, has no
  ACTIVE ban and no block pair either way (api/invites.mjs:48-58). Guarded
  write: `requireUser`, `assertNotBanned`, the write limiter, the JSON size
  cap and `isValidUsername` (:79-84). Pinned in wave 5.34. (The binds comment
  at :52 says "claimant id (x2)"; the statement binds the ref key, the
  claimant id and the window start — three binds. Comment only.)
- **Invite enumeration.** Every refusal is the same `200 { inviter: null }`
  with no write. A fresh account can probe names until one claim lands, but
  the answer ("exists, not banned, not block-paired") is what the profile
  route already answers; after one success the account is done.
- **Invite bell row and welcome line.** The label-only row ("Your friend X
  joined using your invite link") hides while X is actively banned or
  block-paired with the recipient, read-time (api/notifications.mjs:84-98);
  usernames cannot be changed, so the label always names the right account.
  `invitedBy` applies the same rule and never throws (api/invites.mjs:62-76).
- **Invite deletion.** Both columns `ON DELETE CASCADE` (migration 0064);
  deleting either account succeeds and removes the row. Pinned in wave 5.34.
- **Staff-pick writes.** `requireStaff` (mutating: same-origin +
  `X-CSRF-Token`; anon 401, member 403), `assertNotBanned`, the write limiter
  (api/staff-picks.mjs:85-87); the id is `[0-9]{1,15}`; only a public,
  unbanned-author Showcase root can be picked (:42-53). Pinned in wave 5.35.
- **409 semantics.** Picking the current pick is a 409 (:65); unpicking a
  post with no pick is a 409 from `meta.changes` (:76). The current-pick check
  and the insert are not one statement, so two staff picking the same post at
  once can store two rows for it; both name the same post and unpick removes
  all of them, so the race is harmless.
- **Staff-pick log.** `staff_pick_log.post_id` has no reference by design, so
  the record outlives a deleted post; the actor cascades; `action` is CHECKed
  to `pick`/`unpick`; the log read is staff-only with a literal `LIMIT 50`
  (:96-100). Every change writes one row (in the pick's batch; after the
  checked unpick).
- **Staff pick on every read.** `currentStaffPick` re-runs the visibility
  root filter (public, Showcase, author not actively banned, no block pair;
  staff get no hidden bypass) for this viewer on every read, and an older
  pick never stands in (api/traditions.mjs:135-155). The `staffPick` flag on
  post payloads only marks a post the viewer can already read.
- **Staff-pick subquery cost.** The `staff_pick` column is an uncorrelated
  scalar subquery (api/core/shapers.mjs:52); SQLite runs it once per
  statement, on `featured_posts_newest_idx`, bind-free.
- **/week visibility and binds.** Threads: the public root filter plus the
  viewer's block filter, a reply tally that counts only replies a reader
  could see; showcase: the gallery query with a bound window; the pick as
  above. 7 binds at most; previews masked before the cut
  (api/traditions.mjs:59 `previewExcerpt`). Pinned in wave 5.35 and the
  cross-route sweep.
- **New chip.** A boolean computed in SQL from `users.created_at`
  (api/core/shapers.mjs:48); the timestamp itself never leaves the server
  (profiles already show `joinedAt`).
- **Conversation search gate.** `requireSignedInRead` then a participant
  (1:1) or member (group) check; a non-participant gets the exact 404 body a
  missing conversation gets (api/conversation-search.mjs:98-117; group via
  `loadGroupForMember`). Better than the older DM routes, whose 403 for
  non-participants is pre-existing. The `q` length check runs first and does
  not depend on the conversation, and the membership read is one indexed
  query either way, so status and timing do not reveal ids. Pinned in wave
  5.36.
- **Conversation search without an Origin check.** It is a GET with no side
  effect (no write, no log, no storage). The session cookie is `SameSite=Lax`
  and `/api/*` sends no CORS headers, so a cross-site page cannot read the
  JSON; a JSON object body cannot be pulled in as a script. That is the same
  rule every signed-in GET follows (`requireSignedInRead` in api/export.mjs,
  the DM reads).
- **Conversation search query.** Bound `LIKE ? ESCAPE '\'` with `\ % _`
  escaped (:59-61); 2-100 characters; `LIMIT 50`; the chat view's own
  ban/block predicates (`DM_VISIBLE_MESSAGE_SQL`,
  `VISIBLE_GROUP_MESSAGE_SQL`); 4 binds; excerpts masked before the window,
  surrogate-safe. Pinned in wave 5.36 (no console, no writes).
- **Search since/sort.** `since` in `any|week|month|year` via
  `Object.hasOwn` on a frozen map, `sort` in `relevant|new`; anything else is
  a 400 (api/search.mjs:43-53). The cutoff is one bound value; the sort
  changes a fixed `ORDER BY` string. Both feeds stay under
  `D1_MAX_BOUND_PARAMS` at a full page with a blocking viewer (pinned in
  tests/wave32-feed-page-size.test.mjs).
- **share.js after the CodeQL #22 fix.** Every intent URL is built with
  `new URL` on a fixed https host and `searchParams` (share.js:68-73); the
  Mastodon host must match a bare-host pattern and then survive the URL parser
  unchanged on https with path `/share` (:80-90); links get
  `rel="noopener noreferrer"`. No button for staff viewers or non-public or
  non-root posts (:106-111). Pinned in waves 5.34 and 5.35.1.
- **Client storage.** Recent searches: `forum-recent-searches:u<id>`, nothing
  for guests, wiped on sign-out (`clearAllRecentSearches`,
  routes/account-nav.js:281). The invite ref lives in sessionStorage (this
  tab) and is wiped on sign-out and after the claim. The remembered Mastodon
  host is a device preference that is wiped on sign-out anyway. Pinned in
  tests/wave27-storage-wipe-sweep.test.mjs.
- **HTML sinks and CSP.** No `innerHTML`-family sink, `document.write`,
  `eval` or `window.open` was added; new links are `/posts/<Number>`,
  `/users/<encodeURIComponent>` or URL-API built. `index.html` only gained
  four `modulepreload` links; the CSP is unchanged.
- **Migrations 0064 and 0065.** CREATE TABLE / CREATE INDEX IF NOT EXISTS
  only; every user and post reference cascades except the deliberate
  `staff_pick_log.post_id`. Pinned in waves 5.34 and 5.35.
