## L1 — LOW — a status could render reversed past the word filter (FIXED)

- Touches: `PUT /api/me/status` text, shown under the name on every
  profile (public/js/profile-extras.js `createStatusLine`, `textContent`).
- Trust boundary: member-written text shown to every reader of the profile,
  guests included.
- Threat: `normalizeStatusText` refused C0/C1 controls and U+2028/2029 only
  (api/user-status.mjs:48-51 before the fix). The bidi embedding/override
  (U+202A-202E) and isolate (U+2066-2069) controls passed. The word filter
  checks the logical string, so `"‮drowdab"` is not a hit, but the
  browser draws it right to left as the filtered word. The filter itself
  held up against zero-width, soft hyphen, combining marks, fullwidth,
  Cyrillic/Greek homoglyphs and spacing/punctuation tricks (checked by hand
  against `applyWordFilter`, see the passed items).
- Failure scenario: a member puts a filtered slur on their profile as a
  reversed status that every visitor reads the right way round.
- Fix: those nine code points now count as control characters for a status
  (api/user-status.mjs:51-55); the request is a 400 and nothing is stored.
  The plain direction marks U+200E/U+200F stay allowed, and Hebrew, Arabic
  and other right-to-left text is unaffected (the forum ships he, fa and ur).
- Pinned (tests/wave541-security-review.test.mjs): every one of the nine
  code points is refused by the pure helper and by the route with no row;
  RTL text and the plain marks still save.

## L2 — LOW — the 200-follow cap could be raced (FIXED)

- Touches: `POST /api/users/:name/follow`.
- Trust boundary: a member's own writes; the cap bounds what the fan-out
  query and the Following list walk.
- Threat: the route counted the member's follows, then inserted in a second
  statement (api/follows.mjs:127-134 before the fix). Parallel POSTs that
  all read 199 each insert, so the member ends above `FOLLOWING_MAX`.
- Failure scenario: a script fires a burst of follows at the cap. The extra
  follows still fan out (the fan-out reads by followee), but the Following
  list stops at 200 rows (`LIMIT FOLLOWING_MAX`), so the member cannot see or
  undo them from the page. The write limiter bounds the overshoot to one
  burst; no other member is affected.
- Fix: the INSERT carries the cap in its own `WHERE (SELECT COUNT(*) ...) <
  FOLLOWING_MAX` (api/follows.mjs:131-140, 4 binds); when it writes nothing
  and the follow does not exist, the answer is the cap's 400. The earlier
  read stays as the fast path.
- Pinned: with a stale cap read (it reports room while 200 follows exist) the
  201st follow is a 400 and the count stays at 200; a normal and a repeated
  follow still answer `{ following: true }` with one row.

## L3 — LOW — the 20-folder cap could be raced (FIXED)

- Touches: `POST /api/me/bookmark-folders`.
- Trust boundary: a member's own private rows.
- Threat: the same read-then-write shape (api/bookmark-folders.mjs:104-115
  before the fix); parallel creates with distinct names pass the count and
  all insert.
- Failure scenario: folders above 20 exist, but the folder list stops at
  `LIMIT FOLDERS_MAX`, so they are invisible and cannot be renamed or deleted
  from the page (their items cascade only with the account).
- Fix: the INSERT carries the cap (api/bookmark-folders.mjs:108-119, 4 binds);
  zero changes is the cap's 400. A duplicate name is still the UNIQUE 409.
- Pinned: with a stale cap read the 21st folder is a 400 and the count stays
  at 20; a duplicate name is still 409 and a fresh name 201.

## O3 — LOW — the data export leaves out what v5.38-v5.40 lets a member set (OWNER DECISION)

- Where: `SECTION_READERS` (api/export.mjs:97-112). Migrations 0066-0068
  added five member-set records: the custom status (`user_status`), the
  profile pin (`profile_pins`), the follow list (`user_follows`, the
  member's own direction), the bookmark folders with their items
  (`bookmark_folders`, `bookmark_folder_items`) and the notification mutes
  (`notification_prefs`). None of them is in the download.
- Why it is a gap and not a defect: unlike O2, these sit inside the export's
  written scope ("what THEY wrote and set", api/export.mjs:20-37), but adding
  sections changes the export format, which earlier reviews left to the
  owner. Every row is own-only, never public beyond the status and pin the
  profile already shows, and all of them cascade on account deletion
  (pinned in waves 5.38-5.40).
- Failure scenario: a member who downloads their data to see everything the
  forum keeps about them gets no record of whom they follow or of their
  folders, status, pin or mutes.
- Options: (a) add the five sections (follows as usernames with the time,
  folders as name + post ids, the rest as stored); (b) add only follows and
  folders (the ones the member cannot read back in one place); (c) keep the
  scope and say so in the privacy text. It can ship with whatever is picked
  for O2.

## A1 — LOW — one new thread can write up to 500 bell rows (ACCEPTED)

- A new public root runs `FANOUT_INSERT_SQL` (up to `FOLLOW_FANOUT_CAP` = 500
  rows) and `FANOUT_PRUNE_SQL` (trims each of those followers back to 50
  rows) in one batch (api/follows.mjs:61-91, api/posts-write.mjs:342-352).
  A member followed by 500+ accounts turns each thread into ~1000 row writes.
- Accepted: the fan-out only reaches people who chose to follow the author;
  thread creation is behind the shared write tier plus the per-member
  `post-write` limiter and Turnstile when configured; both statements are
  fixed-bind (5 and 1) with no IN list; follower 501+ simply gets no row.
  A member following 200 accounts adds nothing per thread of their own.
  Replies never fan out (the INSERT requires `parent_id IS NULL`), and a
  staged (hidden) root writes nothing (pinned in wave 5.39). It sits with O1
  as a write-volume item, not an exposure.

## A2 — LOW — the follow prune can trim an old safety notice (ACCEPTED)

- The prune keeps each notified follower's newest 50 rows, label-only rows
  included (api/follows.mjs:76-81). An appeal outcome is a label-only row, so
  50 newer rows push it out — the same rule every reply, mention and
  subscription fan-out has applied since v4.2.
- Accepted: actively banned followers are never eligible (api/follows.mjs:61-65),
  so a pending or denied appeal notice of a banned member is never trimmed by
  this fan-out. An approval notice can be trimmed only after the member is
  unbanned and 50 newer rows arrive from accounts they chose to follow or
  posts they wrote; the ban banner is gone by then, so the outcome is
  visible without the row. Mutes (v5.40) never apply to appeal outcomes
  (pinned in wave 5.40).

## A3 — LOW — status text can stack combining marks or use letters the filter does not fold (ACCEPTED)

- `normalizeStatusText` caps at 60 code points (api/user-status.mjs:69-76),
  so up to 59 combining marks can stack on one letter and draw over the
  lines around it; letters outside the filter's homoglyph map (for example
  small capitals such as U+1D05) pass it.
- Accepted: post bodies, bios, flair and pronouns accept the same text today;
  the status is a profile-only line the member writes about themselves;
  reporting a profile works as for any other field. A dedicated fix belongs
  with the filter (one change for every surface), not with one field.

## A4 — LOW — folder names are unique only byte for byte (ACCEPTED)

- `UNIQUE (user_id, name)` uses binary collation while the list sorts with
  `COLLATE NOCASE` (api/bookmark-folders.mjs:96), so "Work" and "work", or an
  NFC and an NFD spelling, can coexist.
- Accepted: folders are private to their owner (every route keys on
  `(id, user_id)`), so two similar names can only confuse the person who made
  them; control characters are already refused.

## Checks that passed

- **v5.37 invite-claim CSRF order.** Reviewed and fixed in the previous
  review (L1 there); unchanged here and still pinned by
  tests/wave537-security-review.test.mjs.
- **Status writes.** `requireUser` (same-origin + `X-CSRF-Token`),
  `assertNotBanned`, the write limiter keyed by member (api/user-status.mjs:136-140);
  5 binds on the upsert, 1 on DELETE. Pinned in wave 5.38 (no Origin 403,
  anon 401, banned 403, 429).
- **Status emoji.** Trimmed, at most 16 UTF-16 units, made only of
  pictographs, ZWJ, VS16, skin tones and regional indicators, holding a
  pictograph or a flag pair, and exactly one grapheme by `Intl.Segmenter`
  (api/user-status.mjs:45-66). Letters, digits, `<`, two emoji and a lone
  regional indicator are refused. Pinned in wave 5.38.
- **Status word filter.** A hit is refused at write, never stored masked
  (api/user-status.mjs:129); words added later are masked at read
  (`readStatus`). Hand-checked against `applyWordFilter`: zero-width
  (U+200B-200D, U+2060, U+FEFF), soft hyphen, invisible operators, tag
  characters, Mongolian vowel separator, Hangul fillers, combining marks
  (U+0300-036F, U+1AB0, U+20D2), fullwidth letters, Cyrillic/Greek
  homoglyphs and spaced/dotted spellings are all caught. The reversed
  display was the one gap (L1).
- **tzOffset and expiry.** `tzOffset` must be an integer within ±840 minutes
  or the PUT is a 400 (api/user-status.mjs:94-100); "today" is the next local
  midnight, so the expiry is always within (now, now + 24 h] whatever offset
  is sent — it can neither go back in time nor stretch past a day. Other
  expiries are fixed offsets from a server clock; "never" is the explicit
  choice. Expiry is compared with a bound "now" at read (no cron). Pinned in
  wave 5.38 (boundary under a fake clock).
- **Status read.** Expired rows and actively banned members drop in SQL
  (api/user-status.mjs:105-118, 2 binds); the status rides only the visible
  profile branch, after the block-pair refusal (api/profiles.mjs:148-149).
  Pinned in wave 5.38 (banned hidden even from staff, block pair, later
  filter words).
- **Profile pin writes.** `requireUser`, `assertNotBanned`, write limiter;
  `postId` a positive safe integer; only the member's own public root
  (another member's or a missing post is the same 404, a reply or hidden
  thread 400) (api/profile-pin.mjs:51-85). Pinned in wave 5.38.
- **Profile pin read.** Re-checked on every read: own root, public (even for
  staff), author not actively banned, 1 bind (api/profile-pin.mjs:36-49);
  block pairs never reach it. The client masks spoilers before it cuts the
  excerpt (public/js/profile-extras.js:51). Pinned in wave 5.38 (hidden
  later, banned, unban restores, cascade).
- **Poll deadline: who.** Setting or clearing `closesIn` goes through the
  close route: root author or staff only (api/polls.mjs:142), signed in +
  CSRF via `pollForWrite`; others 403, anon 401. Pinned in wave 5.38.
- **Poll deadline: race.** The vote INSERT and the unvote DELETE carry
  `POLL_OPEN_SQL`, which now includes `POLL_DEADLINE_AHEAD_SQL` with "now"
  bound in the same statement (api/polls.mjs:119-120, :270;
  api/poll-deadlines.mjs:34-35). A vote that passes the early check and
  lands after the deadline writes nothing and answers 409. Pinned in wave
  5.38 (at/after `closes_at` refused).
- **Poll deadline: bounds.** `closesIn` is a safe integer from 3600 to
  2,592,000 seconds or `null` (api/poll-deadlines.mjs:38-45), validated before
  any write on create (api/polls.mjs:222) and on the manage path; a closed or
  expired poll cannot get a new deadline (409, api/polls.mjs:150). The
  deadline is server time plus a duration, so client clocks never matter.
- **Follow enumeration.** A missing member, an actively banned member and a
  block pair in either direction all give the same `404 Member not found.`
  with no write (api/follows.mjs:51, :125); following yourself is a 400. The
  extra probe for a banned target is one indexed read, and the profile route
  already shows the ban banner for an existing banned member, so neither the
  status nor the timing tells anything new. Pinned in wave 5.39.
- **Follow state read.** `GET /api/users/:name/follow` answers only the
  caller's own state and refuses a block pair (staff excepted) with the same
  404 (api/follows.mjs:147-153).
- **Follow fan-out visibility.** One INSERT…SELECT: the post must be this
  author's own public root with no active ban on the author; followers who
  are actively banned, block-paired either way, muted for `follow_thread`, or
  already holding a row for the post (an @mention) are skipped
  (api/follows.mjs:61-74). The bell's read-time filter re-checks the target
  post afterwards. Pinned in wave 5.39 (banned, block pair, mentioned twin,
  replies, staged root) and wave 5.40 (muted).
- **Follow fan-out binds.** 5 and 1 binds, no IN list, `LIMIT 500` inside the
  subquery; pinned under `D1_MAX_BOUND_PARAMS` in wave 5.39.
- **Notification label injection.** The label is the fixed prefix plus the
  author's username (validated, immutable, 24 chars at most); the client
  localises a label only when it starts with that prefix
  (public/js/notifications.js:78) and renders it with `textContent`. No other
  server label starts with "New thread from ".
- **Block removes follows.** The block INSERT and the two-way unfollow are
  one batch (api/blocks.mjs:62-68). Pinned in wave 5.39.
- **Following list privacy.** Own list only, banned and block-paired
  followees drop at read time, `LIMIT 200`; no route serves anyone else's
  follows or followers, and profiles carry no follow data. Pinned in wave
  5.39.
- **Folder IDOR.** Every folder route resolves `(id, user_id)` first
  (`ownFolder`, api/bookmark-folders.mjs:75-81); the id is `[0-9]{1,15}`;
  another member's folder — staff included — is the same 404 a missing one
  is, for list, rename, delete, items and item writes. Pinned in wave 5.39.
- **Folder contents.** Only posts the owner still bookmarks and that pass
  the bookmarks list's own `visibleSavedFilter` (public, unbanned, visible
  ancestors, block pairs both ways); `FEED_PAGE_SIZE` per page on an
  anchored `^[0-9]{1,10}_[0-9]{1,10}$` cursor; 12 binds at most; images via
  `attachmentRowsForView` (api/bookmark-folders.mjs:183-213). Pinned in wave
  5.39.
- **Folder item add.** The post must be bookmarked by the caller and pass
  `canViewPost`, else 404 (api/bookmark-folders.mjs:147-158); idempotent.
- **Mute list parsing.** The stored list is written only from the validated
  allowlist joined with commas (api/notifications.mjs:228-254); `mutedKindSql`
  matches `,kind,` inside `,list,` with the kind as an allowlist literal that
  binds nothing (:51-55). `mention` cannot match `chat_mention` (the comma
  delimiters), a crafted value like `",reply,"` or `"reply "` is a 400 at
  PUT, and unknown stored entries are dropped at read (:221-226). Pinned in
  wave 5.40.
- **Safety notices stay unmutable.** `notifyStatement` with no kind is a
  plain INSERT (api/notifications.mjs:205-212); appeal outcomes call it with
  no kind (api/appeals.mjs:61, :81); the PUT refuses any kind outside the six.
  Pinned in wave 5.40 (an appeal outcome reaches a member who muted all).
- **Mute list size.** At most 24 entries in the body (`MAX_PREFS_ENTRIES`,
  api/notifications.mjs:46), deduplicated into allowlist order; the PUT is
  signed in + CSRF, not banned, write limited; GET is own row only.
- **Client sinks, links and storage.** No `innerHTML`-family sink,
  `document.write`, `eval` or `window.open` added. New links are built with
  the URL API (`threadPath`, `profilePath`, `folderHref`) from numeric ids
  or `encodeURIComponent` usernames. Folder names, status text and labels go
  through `textContent`. The skip link and easy-reading spacing are
  page-view or device-preference only (`forum-easy-reading`, read in
  theme-preload.js only for an exact "on"). No new account-scoped storage key.
- **Migrations 0066-0068.** CREATE TABLE / CREATE INDEX IF NOT EXISTS only;
  every user and post reference is `ON DELETE CASCADE`; length CHECKs back
  the status text/emoji and folder names. Pinned in waves 5.38-5.40.
