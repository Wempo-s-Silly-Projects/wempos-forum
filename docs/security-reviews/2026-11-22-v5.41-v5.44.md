## M1 — MEDIUM — slow mode is a check-then-insert, so a burst of parallel replies passes it (OWNER DECISION)

- Touches: `POST /api/posts/:id/replies` and the MCP `reply` tool in any
  thread staff put in slow mode.
- Trust boundary: a member's writes against a moderation control staff set
  on a thread.
- Threat: `assertSlowModeAllows` (api/staff-tools.mjs:76-80) reads whether
  the member has a reply in the thread younger than the cooldown, and the
  INSERT runs later in a separate batch (api/replies.mjs:160, then :167-178;
  api/mcp.mjs:634, then :637). Requests that arrive together all read "no
  recent reply" and all insert. This is the same shape as the follow and
  folder cap races fixed in wave 5.41 (L2/L3 there).
- Failure scenario: staff set a 15-minute slow mode to calm a heated thread.
  A script fires 20 replies at once; all 20 land. The next burst is refused
  until the cooldown passes, so the control degrades from one reply per
  window to one burst per window. The burst is capped by the
  `POST_WRITE_RATE_LIMITER` (20 per 60 s per member) and the shared write
  tier (45 per 60 s), which apply with or without slow mode; nothing is
  exposed, and staff can still hide, lock or ban.
- Why MEDIUM and not LOW: unlike the wave 5.41 caps, the thing bypassed is
  a moderation tool meant to stop exactly this kind of flood.
- Recommendation: carry the predicate inside the reply INSERT itself — add
  `AND NOT EXISTS (<the SLOW_MODE_CHECK_SQL body>)` to the `WHERE` of
  `THREAD_REPLY_INSERT_SQL` / `THREAD_REPLY_INSERT_STAGED_SQL` (3 more binds,
  about 19 total), skipped for staff; zero changes plus a fresh hit answers
  the existing 429 `slow_mode`. Keep the early read as the fast path. D1
  runs each statement atomically, so parallel inserts then serialise on the
  check.
- Pinned (tests/wave545-security-review.test.mjs): a `todo` test models
  the race with a stale check read (as wave 5.41 did for the caps) and fails
  today: two replies land inside one cooldown. It turns green when the fix
  lands.

## O4 — LOW — staff notes are erased when the staff member who wrote them is deleted (OWNER DECISION)

- Where: `member_notes.author_id REFERENCES users(id) ON DELETE CASCADE`
  (migrations/0069_staff_tools.sql). Wave 5.43 pinned this as intended.
- Failure scenario: an admin who wrote a member's history of warnings
  leaves and their account is removed; every note they wrote about every
  member goes with it, and the remaining staff lose that context without
  being told.
- Options: (a) keep (the current, pinned behaviour); (b) a new table or
  column dance so the note survives with a null author shown as "former
  staff" (a schema change: the D1 FK law means a COLUMN dance, not an ALTER
  of the FK); (c) keep the cascade but warn on the desk before a staff
  account with notes is deleted. Notes about a member still go with that
  member's own account (correct: nothing should outlive the person).

## O5 — LOW — "Download my data" leaves out the staff notes kept about the member (OWNER DECISION)

- Where: `SECTION_READERS` (api/export.mjs:97-118) has no `member_notes`
  reader, by design (api/staff-tools.mjs:31-33: "Notes never leave these
  routes"). Pinned in this wave: a member's export, the noting staff
  member's export and the profile carry no note text.
- Why it is a question and not a defect: the export's written scope is
  "what THEY wrote and set" (api/export.mjs:20-37), and notes are written by
  staff. But notes are information the forum keeps about the member, which
  some privacy laws let the member ask for.
- Options: (a) keep notes staff-only and say in the privacy text that staff
  may keep moderation notes, available on request; (b) add a `staffNotes`
  section (body and date, no staff names); (c) add only the count. Can ship
  with O2 and O3.

## O6 — LOW — a thread's author can file it under any staff-made tag (OWNER DECISION)

- Where: `setThreadTags` lets the root's author or staff pick any existing
  tag (api/tags.mjs:154-176).
- Failure scenario: staff make an "announcements" or "guides" tag meant as a
  curated list. A member tags their own off-topic or self-promotion thread
  with it and it sits in that tag page until staff notice. Nothing is
  exposed: the listing still obeys the visibility law, and staff can retag,
  hide or remove the tag.
- Options: (a) keep (tags are a member tool, staff only make the list);
  (b) a per-tag "staff only" flag (new column via a CREATE-only table, plus
  a check in `setThreadTags`); (c) tags settable by staff only.

## A1 — LOW — the slow-mode lookup walks all of the author's replies (ACCEPTED)

- `SLOW_MODE_CHECK_SQL` (api/staff-tools.mjs:67-72) enters on
  `idx_posts_author (author_id, parent_id, visibility, id DESC)` and filters
  `created_at` and the thread after the seek, so its cost grows with the
  member's total reply count, once per reply in a slow-mode thread.
- Accepted: only the replying member pays, only in slow-mode threads, and
  only with no table scan (pinned in wave 5.43). If it ever shows in CPU
  time, bound it by id (the newest replies come first in the index) or add
  an `(author_id, created_at)` index.

## A2 — LOW — tag labels are filtered only at create and accept bidi controls (ACCEPTED)

- `readNewTag` (api/tags.mjs:79-92) word-filters the slug and label when the
  tag is made; a word added to the filter later is not masked at read (the
  status does mask at read), and the label may hold the U+202A-202E /
  U+2066-2069 controls wave 5.41 refused for statuses.
- Accepted: only staff write labels (staff are the trust boundary for the
  filter list itself); labels render through `textContent`
  (public/js/tags.js:67-79) and are escaped in the page head (pinned in this
  wave); 50 tags at most, each deletable from the desk. The shared bidi item
  under "Out of scope" covers the general fix.

## A3 — LOW — report claims are advisory (ACCEPTED)

- Any staff member can release anyone's claim (api/staff-tools.mjs:134-138),
  and a claim does not stop another staff member resolving the report. A
  claim held by a staff member who is later demoted stays until someone
  releases it or the report closes.
- Accepted: the claim is a coordination hint between trusted staff; every
  resolve and dismiss path already clears it (api/reports.mjs:122, :136;
  api/mod-tools.mjs:120-123), and a stale claim never hides a report from
  the queue.

## A4 — LOW — slow mode switches off if the staff member who set it is deleted (ACCEPTED)

- `thread_slowmode.set_by` cascades (migrations/0069_staff_tools.sql), so
  removing that staff account silently ends the thread's slow mode.
- Accepted: account removal of staff is rare and deliberate, and the thread
  page shows the slow-mode line, so its absence is visible; staff can set it
  again in one step.

## Checks that passed

- **Staff-tools authz.** Every route is `requireStaff` (owner/admin):
  anonymous 401, members 403; writes add same-origin + `X-CSRF-Token`,
  `assertNotBanned` and the write limiter (api/staff-tools.mjs:54-59). Ids
  are `[0-9]{1,15}`. Pinned in wave 5.43.
- **Staff notes stay staff-only.** `member_notes` is referenced by
  api/staff-tools.mjs alone in api/, public/js/, worker.mjs and
  constants.mjs (no profile, feed, search, export, MCP or page-head join);
  bodies render with `textContent` (public/js/desk/staff-tools.js:74).
  Pinned in this wave (static source sweep plus profile and both exports).
- **Note writes.** `requiredText` caps at 500; the INSERT is guarded by the
  member's existence in the same statement (4+1 binds); DELETE keys on
  `(id, member_id)` and checks `changes` (api/staff-tools.mjs:170-206).
- **Claim race.** One `INSERT … SELECT … WHERE status = 'open' ON CONFLICT
  DO NOTHING` on the `report_id` primary key; zero changes reads back who
  holds it (same staff 200, other staff 409, closed/missing 404)
  (api/staff-tools.mjs:118-132). Pinned in wave 5.43 (2 and 8 concurrent
  claimers).
- **Claims clear on close.** Hide, dismiss and the bulk hide-recent delete
  the claim in the same batch as the status change (api/reports.mjs:111-141,
  api/mod-tools.mjs:116-124); the bulk DELETE binds the same id list as the
  UPDATE beside it, so it adds no bind risk. The queue shows the claimer's
  username only to staff (api/reports.mjs:72-106).
- **Slow mode: who and what.** Staff only; `seconds` must be one of 30, 60,
  300, 900 (route allowlist and table CHECK); roots only
  (api/staff-tools.mjs:82-105). The thread payload carries only the seconds;
  who set it and when never leave the desk (api/core/shapers.mjs:55, :260;
  pinned in this wave).
- **Slow mode: every reply path.** The web reply route and the MCP reply
  tool both call `assertSlowModeAllows` on the conversation root
  (api/replies.mjs:160, api/mcp.mjs:634); level-2 replies and the
  reply-reparent on delete are covered by the `p.parent_id = root OR
  par.parent_id = root` test; staff exempt, moderators not. Idempotent
  replays return before the check (api/replies.mjs:116-117), so a retried
  reply is not refused. The only other `INSERT INTO posts` is the root
  insert (parent NULL). Bound params only, 3 binds. Pinned in wave 5.43.
- **DM reactions: who.** Session + CSRF, not banned, reaction limiter, then
  the message must exist, belong to a 1:1 thread the caller is in, and have
  an author with no active ban (api/dm-reactions.mjs:47-62). Anyone else —
  staff included — gets the same 404 as a missing id (pinned byte for byte
  in this wave); the 403 for a block pair is only reachable by a
  participant, so it tells them nothing new.
- **DM reactions: read.** One grouped query per thread page, bounded to the
  page's id range in that thread, 4 or 5 binds; reactions by actively banned
  members drop, and across a block pair or a banned other side only the
  viewer's own reactions remain (api/dm-reactions.mjs:89-111,
  api/chat.mjs:382-395). The thread read's participant gate runs first.
  Pinned in wave 5.44.
- **DM reactions: values and storage.** `REACTION_VALUES` (constants.mjs)
  is checked by the route and mirrored by the table CHECK; one row per
  member per message (primary key); reactions send no notification.
- **DM reaction export.** Only the caller's own rows (message id, value,
  time), never the other participant's text, capped at 2000
  (api/export.mjs:115-117, :164). Pinned in wave 5.44.
- **Tag CRUD.** Staff only with CSRF, not banned, write limited; slug
  `^[a-z0-9-]{2,24}$`, label 1-24 code points, both word-filtered; the
  50-tag cap and the duplicate slug are enforced inside the INSERT (no
  read-then-write race) (api/tags.mjs:79-119).
- **Thread tagging.** The author or staff only, root only, on a post the
  caller can view (hidden or banned threads 404 to members), ids validated

  the replace is one batch (api/tags.mjs:138-176). Pinned in wave 5.44.
- **Tag listing visibility.** Roots only, `visibility = 'public'` for

- **Tag listing binds and paging.** `FEED_PAGE_SIZE` rows on an anchored
