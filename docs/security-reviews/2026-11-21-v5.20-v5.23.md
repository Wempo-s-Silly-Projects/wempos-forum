## S1 — MEDIUM — pronouns not re-filtered at read (FIXED)

- Where: api/profiles.mjs:139 served `readPronouns()` raw. Flair and banner
  text on the same payload pass through `applyWordFilter` at read
  (api/profiles.mjs:128-129).
- Scenario: pronouns are word-filtered only on write (api/pronouns.mjs:78).
  A member saves pronouns that pass today's filter; staff later add the word
  to the filter. Flair and banner text are masked from then on; pronouns keep
  showing the word. There is no staff route that edits or clears another
  member's pronouns, so the filter is the only staff remedy short of a ban
  or account deletion — and it did not reach this field.
- Fix: one expression — the profile payload now serves
  `applyWordFilter(await readPronouns(...), filterWords(env)) || ""`
  (api/profiles.mjs:141), the same shape as flair. The write-side refusal
  (400 `pronouns_not_allowed`) is unchanged. Download my data still returns
  the member's own saved value, as it does for flair.
- Tests: tests/wave524-security-pins.test.mjs "S1: pronouns saved before a
  word joined the filter are masked on the profile" (RED at 4364fcd before
  the fix).

## L1 — LOW — pronouns edits are not fed to AutoMod (ACCEPTED)

- Where: `PUT /api/me/pronouns` (api/pronouns.mjs:64) does not call
  `recordProfileEdit` the way `PATCH /api/me` does. When AutoMod is on, a
  pronouns change does not show up in its profile-edit queue. The field is
  24 characters of letters, spaces, `/` and `-`, word-filtered on write and
  now on read (S1). Accepted: adding a new collection point is a behaviour
  change outside a security-fix lane.

## L2 — LOW — checkout keeps the job token in .git/config (ACCEPTED)

- Where: the checkout step of audit.yml, gitleaks.yml, semgrep.yml and
  shellcheck.yml has no `persist-credentials: false` (zap-baseline.yml and
  reuse.yml do). Every one of these workflows is `permissions: contents:
  read`, runs on `push`/`pull_request` (never `pull_request_target`), and
  pins every action to a commit SHA, so the persisted token is read-only
  and fork PRs get GitHub's read-only token anyway. Accepted; a hardening
  follow-up can add the flag.

## I1 — INFO — setup can stage an inert pending secret while 2FA is on

- Where: api/twofa.mjs:121. If a setup's password/enabled read sees 2FA off
  and a confirm in another tab commits before the setup's batch, the batch
  still writes `totp_pending_secret`. It is inert: the algorithm upsert in
  the same batch is gated on `totp_enabled = 0` (api/twofa.mjs:124), confirm
  requires `totp_enabled = 0` (api/twofa.mjs:156), and disable clears it.
  The live secret and algorithm are untouched and sign-in keeps working
  (pinned).

## I2 — INFO — Semgrep rule packs are fetched by name

- The container image is digest-pinned, but `--config p/javascript` etc.
  download the current registry rule packs each run. Rules can change
  between runs (a new finding can fail a PR with no code change). No secret
  or write access is involved. No fix.

## Checks that passed

- **TOTP algorithm (v5.20.0).** `normalizeTotpAlgorithm` maps anything but
  the exact string `SHA256` to `SHA1` (api/core/totp.mjs), and the table's
  CHECK only admits those two. Setup writes the staged secret and the
  algorithm in one batch; the upsert is gated on `totp_enabled = 0`
  (api/twofa.mjs:118-124), and setup is refused with 409 while 2FA is on.
  Confirm reads secret + algorithm in one statement and promotes only the
  secret it verified (`totp_pending_secret = ?`, api/twofa.mjs:156), so a
  setup re-run racing a confirm makes it 409. Disable, backup-code
  regeneration and the login step each read the algorithm in the same row
  as the secret (api/twofa.mjs:180, 214, 283); disable deletes the row in
  the same batch (api/twofa.mjs:192). Password sign-in (api/session.mjs:260)
  only checks whether 2FA is on. No other code path writes `totp_enabled`
  or `totp_secret`. Account deletion cascades the row (FK). Pinned: confirm
  racing setup, setup racing confirm, setup with an algorithm while on.
- **Export (v5.20.0, v5.23.0).** Only the algorithm name (when 2FA is on)
  and the member's own pronouns are added (api/export.mjs:86, 91). No secret,
  pending secret or backup-code hash appears; no key named `*secret*`
  (pinned).
- **Pronouns route (v5.23.0).** `requireUser` (same-origin + CSRF),
  `assertNotBanned`, the write rate limit, `readJson` size cap, then the
  server-side pattern `^[A-Za-z][A-Za-z /-]{0,23}$` and the word filter
  (api/pronouns.mjs:33-78). Binds only, keyed on the session's own user id.
  The block-pair refusal returns before pronouns are read; banned members'
  pronouns follow the existing profile rule (shown with the banner, like
  the bio). The client paints them with `textContent` only
  (profile-extras.js `createPronouns`). Pinned: an XSS string is refused
  (400) and a markup value forced into the table round-trips as text.
- **Source link (v5.21.0).** `httpsUrlOrEmpty` accepts only `https:` with no
  credentials (api/core/source-url.mjs:39); otherwise the link is the
  repository tree at a hex `COMMIT_SHA`, or no meta. The meta goes through
  `attributeEscape` (worker.mjs:127, 141). The client re-checks the same rule
  and sets the href with `setAttribute` (public/js/source-link.js:35).
  Pinned end to end: `javascript:`, mixed-case `JaVaScRiPt:` and `http:`
  values never reach the href.
- **Print stylesheet (v5.23.0).** The footer paragraph is
  `visibility: hidden` and `.site-footer [data-source-link]` is
  `visibility: visible` (public/styles.css:3511); no print rule sets
  `display: none` on the footer, its paragraph, links or the source link
  (pinned), so the AGPL §13 link prints.
- **CI (v5.21.0–v5.22.0).** All six new workflows are top-level
  `permissions: contents: read`, trigger on push/pull_request/schedule/
  workflow_dispatch only, and pin every action (and the ZAP and Semgrep
  images) to a full SHA or digest. The ZAP job writes a throwaway
  `.dev.vars` at run time with the public dummy pepper
  `ci-only-not-a-secret-pepper`, scans `http://localhost:8787`, reads no
  repository secret and cannot open issues (pinned). gitleaks is
  checksum-verified. claude.yml and claude-code-review.yml only moved
  `actions/checkout` from a tag to a SHA.
- **Migrations 0061/0062.** CREATE-only, `ON DELETE CASCADE` to users,
  CHECK constraints on algorithm and pronouns length. No existing table
  altered.
