## L3 — LOW — a reply refused by the slow-mode guard still bumps the thread

- Touches: `POST /api/posts/:id/replies` (no attachments) and the MCP
  `reply` tool.
- Threat: both paths send the guarded INSERT and `REPLY_BUMP_SQL`
  (constants.mjs:67-70) in one `db.batch`. The bump is conditioned only on
  the root being public and having some public reply, not on the INSERT in
  front of it. Since v5.54 the INSERT can refuse a slow-mode race (0 rows),
  and the bump still sets the root's `last_activity_at` to now. The same
  shape already applied to the INSERT's older refusals (a ban or an
  archived idempotency key landing between the read and the write); v5.54
  adds a cause any member in a slow-mode thread can reach.
- Failure scenario: a member in a slow-mode thread fires two replies at
  once. One lands; the other gets 429 `slow_mode`, but the thread moves to
  the top of the "active" feed a second time. Repeating it inside the
  cooldown bumps the thread without adding a reply. Nothing is exposed and
  no reply is written; the post-write limiter caps the rate.
- Recommendation: condition the bump on the reply row, for example
  `AND EXISTS (SELECT 1 FROM posts r WHERE r.parent_id IN (posts.id, …) AND
  r.author_id = ? AND r.created_at = ?)`, or split the bump into a second
  statement sent only when `meta.changes` is 1 (the staged path already
  bumps after the fact through `STAGED_REPLY_BUMP_SQL`). No schema change.
- Pinned: `todo` in tests/wave557-security-review.test.mjs (web and MCP);
  it fails today as expected.

## L4 — LOW — the settings hub's heading outline is flat

- Where: the hub is an `h1` (feed.js:164), each group an `h2`
  (settings-groups.js:69-77), and each panel keeps its own `h2`. So a
  screen reader's heading list shows the four group names and the 14 panel
  names at the same level, and the groups do not nest their panels.
- Failure scenario: a screen reader user jumping by heading level 2 hears
  "Appearance & reading", "Appearance", "Reading comfort", "Notifications"
  … with no way to tell groups from panels. The `aria-labelledby` on each
  group `section` still names the region.
- Recommendation: make the panel titles `h3` inside the hub, and match
  `settingsGroupFor` on `h3` (it reads `querySelector("h2")` today, so the
  two must change together, with the tests that pin panel titles).

## L5 — LOW — a toggle inside More closes the menu and drops focus

## M1 — slow mode inside the reply INSERT (VERIFIED FIXED IN v5.54)

- **Bind order.** `SLOW_MODE_INSERT_GUARD_SQL` is `" AND NOT EXISTS (" +
  SLOW_MODE_CHECK_SQL + ")"`, appended after the INSERT's last clause.
  The base INSERT's WHERE is a chain of `EXISTS … AND NOT EXISTS … AND (…)`
  with the last term parenthesised, so the appended `AND` joins the chain
  and cannot regroup an `OR`. Its three placeholders appear in text order
  root id, author id, now, and `withSlowModeGuard` appends exactly
  `[Number(rootId), Number(user.id), now]` (staff-tools.mjs:87-91). Members
  bind 15+3 (plain) or 16+3 (staged), staff stay at 15/16; all far below
  `D1_MAX_BOUND_PARAMS`. The check uses the same `now` as the reply's
  `created_at`, so the predicate matches the early check exactly. Pinned in
  wave 5.54 by capturing the real statement.
- **Staff exemption.** `isStaffRole` returns the SQL and values unchanged
  for owner/admin, the same test `assertSlowModeAllows` uses, so staff skip
  both the early read and the guard (wave 5.54).
- **Both paths.** The web route guards both INSERT variants
  (api/replies.mjs:171-175); the MCP tool guards its one INSERT
  (api/mcp.mjs:639-641). On 0 rows, the web route keeps its idempotency
  replay and 410 checks first, then answers 429 `slow_mode`; MCP answers
  the slow-mode text as a tool error (pinned in this wave). A burst of five
  stale-read replies lands exactly one (wave 5.54, wave 5.45 now real).
- **Plan.** `EXPLAIN QUERY PLAN` of both guarded INSERTs shows no table
  scan: the thread row is a primary-key read, the author's replies come off
  `idx_posts_author`, parents by rowid (wave 5.54).
- The one gap left is L3 (the bump in the same batch).

## M2 — diff budget (VERIFIED FIXED IN v5.54)

`DIFF_PANEL_CELL_BUDGET` is one worst-case diff (2000 x 2000 cells).
`diffWordsWithin` trims the common prefix and suffix, computes the table
size and returns null before allocating when it would exceed what is left,
so one panel never builds more than the budget in LCS cells; versions past
it show plain, masked text (render.js:735-740). Tokenising every version is
linear and capped at `DIFF_MAX_WORDS`. Pinned in wave 5.54 (100 worst-case
edits, and many small edits still all diffed). The edits route still has no
LIMIT (out of scope, unchanged).
