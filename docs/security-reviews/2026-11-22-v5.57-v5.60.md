## L7 — LOW — the nav reuse could keep a bell that "Mark all read" had cleared (FIXED IN v5.61)

- Where: v5.60 reuses the header and phone bar when the key (role,
  username, role name, unread count, path, query) matches the last build
  (account-nav.js `canReuseNav`). But `markAllNotificationsRead`
  (routes/notifications.js:74) calls `updateBell(0)`, which edits the built
  bell in place: it hides the dot and sets the label to "Notifications".
  The key still holds the unread count the bell was built with.
- Failure scenario: a member has one unread notification and presses Mark
  all read. A new notification lands between the read-all POST and the
  re-render's `GET /api/session`, which answers 1 again. The key matches,
  the nav is reused, and the bell shows no dot and reads "no unread" while
  the server says one. It heals on the next navigation (the path is in the
  key). Only the member's own count is involved; nothing is exposed.
- Fix: the build also records the bell node and its `aria-label`;
  `canReuseNav` rebuilds when the bell no longer carries that label.
  `updateBell` always changes the label together with the dot, so any
  in-place edit that changes what the bell shows forces a rebuild. The v5.60
  perf pins (no nodes, no listeners on an unchanged re-render) still pass.
- Pinned: tests/wave561-security-review.test.mjs "L7: after Mark all read
  edits the bell in place, an equal unread count from the session still
  repaints the dot" (RED against v5.60, green after the fix), and "L7: the
  reuse still holds when nothing touched the bell".

## L8 — LOW — a failed bump after a landed reply answers 500 and skips the fan-out

- Touches: `POST /api/posts/:id/replies` (no attachments) and the MCP
  `reply` tool.
- Threat: since v5.59 the bump is its own statement after the INSERT has
  committed (api/replies.mjs:199, api/mcp.mjs:650), no longer in the same
  batch. That is what fixes L3, and it is the right trade: the bump is
  cosmetic (it orders the "active" feed), and binding it to the reply row
  means a refused reply can never move a thread. The cost is that the two
  writes are no longer atomic, and the bump's `await` is not guarded. If
  that one statement fails (a transient D1 error, the isolate dying between
  the two round trips), the reply exists but the handler throws: the web
  route answers 500 and the MCP tool reports an error, and the fan-out after
  it (reply and mention notifications, `replyFanOut` on MCP) does not run.
- Failure scenario: a D1 hiccup on the bump. The member sees an error,
  though the reply is posted; on the web, a retry with the same
  idempotency key replays the stored reply (no duplicate). An MCP agent has
  no idempotency key, so a retry posts the reply a second time. The thread
  author is not notified of the first one. The reply itself obeys every
  visibility rule either way; nothing is exposed.
- Rating: LOW. The window is one failed statement after a successful one;
  the cause needs a backend fault, not an attacker. The other side of the
  non-atomic split is harmless: if the root is hidden between the two
  statements, the bump's `visibility = 'public'` checks refuse it, and a
  reader who loads the thread between the two sees the reply before the
  thread is re-ordered.
- Recommendation: treat the bump as best-effort: catch its error, log it
  with the reply and root ids, and continue to the fan-out and the 201.
  Or send it in one batch with the first fan-out statement. Client and
  schema unchanged either way.

## L3 — slow-mode-refused reply bumped the thread (VERIFIED FIXED IN v5.59)

- **Bind order.** `REPLY_BUMP_SQL` (constants.mjs:72-78) has three
  placeholders, in text order `MAX(…, ?)` (now), `id = ?` (the root) and
  `reply.id = ?` (the new reply). All three call sites bind exactly
  `(now, bumpTargetId, replyId)` (replies.mjs:199, mcp.mjs:650) or
  `(nowSeconds(), bumpTargetId, postId)` (posts-write.mjs:205).
  tests/wave557-security-review.test.mjs captures the real statement and
  pins the three binds on both paths.
- **Sent only after the INSERT.** The batch now holds only the guarded
  INSERT. The bump runs after the `meta.changes !== 1` check, so a 0-row
  INSERT (slow-mode race, ban or archived key landing between the read and
  the write) throws first and never reaches it (wave557 "a raced reply
  refused by the slow-mode guard does not bump the thread", web and MCP;
  the v5.57 `todo` is now a real test).
- **Level-2 root resolution.** `bumpTargetId` is the target when it is a
  root, else the target's parent (replies.mjs:133-148, mcp.mjs:609-618).
  The EXISTS accepts the reply when `reply.parent_id = posts.id` (a reply to
  the root) or `target.parent_id = posts.id` through the LEFT JOIN on the
  reply's parent (a reply to a reply). A reply id that is not under that
  root, or not public, matches nothing. Pinned by wave557 "a level-2 reply
  bumps its conversation root, not the reply it answers".
- **Staged replies.** An attachment-bearing reply is inserted hidden and
  skips the immediate bump; it bumps when its batch publishes, through the
  same statement (`STAGED_REPLY_BUMP_SQL = REPLY_BUMP_SQL`). The `reply.
  visibility = 'public'` check runs after the publish in the same batch.
- **Plan.** The EXISTS is a primary-key read on the reply and its parent
  (wave557 "the row-bound bump is served by primary keys (no table scan)").
- **Non-atomic bump.** Rated LOW as L8 above.

## L4 — settings hub heading levels (VERIFIED FIXED IN v5.58)

Inside the hub each panel's `h2` gets `aria-level="3"`
(settings-groups.js:88-94), so the outline reads hub h1, group h2, panel
level 3. The element stays an `h2` because twofa.js, account-security.js
and `panelTitle` look panels up by `h2`; that is why aria-level was used
instead of an `h3`. Browsers map `aria-level` on a native heading to the
heading level in the accessibility tree. v5.60 also starts the guest
prompt at h1 (pinned in wave560).

## L5 — focus after an action inside More (VERIFIED FIXED IN v5.58)

app.js wraps each `data-action` click in `captureMoreFocus` /
`restoreMoreFocus` (thread-actions.js:185-226), with the restore in a
`finally`. The restore only acts when the More panel was replaced (the
route re-rendered); it reopens More (and Staff), then focuses the same
control, its paired toggle (Pin ↔ Unpin, Lock ↔ Unlock, Pick ↔ Unpick), or
else the More button. It reads and stores nothing, and it never opens a
panel the viewer did not already have: the Staff panel exists only for
staff, so a member's snapshot carries no Staff id. If the action navigated
away, `getElementById` finds no panel and nothing happens.

## Nav reuse (v5.60): can it show stale state?

Verdict: no stale role, user or staff item; one stale-unread case, L7,
now fixed.

- **Role change.** The key carries `navRoleOf(user)` and `user.role`, so a
  promotion or demotion rebuilds both surfaces. The Moderation desk entry
  (`audience: "staff"`) leaves both the Account menu and the phone More on
  the first render after a demotion (wave561 pin).
- **Another account, or signed out.** The key carries the username (unique)
  and the role (`guest` when the session has no user), so a different
  account or a dropped session rebuilds. Sign-out itself is a full page load
  (`window.location.assign` to the Accounts sign-out), so no nav survives
  it; and a guest render has no desk, bell, profile link or sign-out
  control (wave561 pin).
- **Unread.** The key carries the unread count; the one in-place edit of
  the built nav is `updateBell`, now covered by L7's check.
- **Page.** Path and query are in the key, so `aria-current` always follows
  the page.
- **Language.** `setLocale` reloads the page, so a cached nav never shows
  another language.
- **Open menus, replaced nodes.** An open menu, or a header or bar whose
  first child is not the cached node, rebuilds (wave560).

## Navigation reorg (v5.58, v5.60)

Verdict: no regression found. Details:

- **No staff or member item for guests.** `navItemsFor` filters one frozen
  list by audience. Guests get the `all` items, Sign in, and on phones only
  My posts and Alerts (`guestOnMobile`, each a sign-in prompt, as before
  v5.58). `desk` is `staff` only; saved posts, settings, profile, shortcuts
  and sign-out are `member`. The profile href is built only for a member, so
  a guest render never reads `user.username`. Pinned in wave558 and in
  wave561 for a demoted staff member and a signed-out render. These are
  links only: every destination still checks the session on the server
  (`/admin` reads need `requireStaff`).
- **Phone bar parity.** Both surfaces draw from `NAV_ITEMS`; the phone
  More holds the Browse group, then the account group, then the same
  language picker the header uses (wave558, wave560). Every destination is
  reachable on both surfaces for each role (wave558).
- **Duplicate links.** The thread card drops its Copy link only when Share
  exists and its own menu has Copy link (no `navigator.share`); with a
  device share sheet the card keeps it. The Open post link goes only when
  it points at the current path. The capability stays reachable (wave558).
- **Menus and keyboard.** Each menu reuses `createDisclosure` (a real
  `button` with `aria-expanded` and `aria-controls`, a `hidden` panel,
  Escape closes it and returns focus). Groups are `role="group"` with
  `aria-labelledby` on a visible label. The new focusout rule
  (account-nav.js:134) closes a menu only when focus moves to a known node
  outside it; a focusout with no `relatedTarget` (a click on something not
  focusable, as macOS browsers do for links and buttons) is left to the
  outside-click handler, so a pointer click inside the panel cannot close
  it before the click lands (wave560). Element ids are unique: the bell id
  appears in the header only, and the menu panel and group label ids are
  scoped by menu (`nav-browse-panel`, `nav-mobile-group-browse`, …).
- **No new HTML sink.** nav-items.js, account-nav.js, thread-actions.js,
  share.js, settings-groups.js, icons.js and app.js, as changed in the
  range, use no `innerHTML`, `outerHTML`, `insertAdjacentHTML`,
  `document.write`, `DOMParser`, `eval` or `new Function`. Labels go
  through `textContent`, hrefs through `.href` (fixed paths, the Accounts
  handoff from sso.js, or `/users/` + `encodeURIComponent(username)`).
- **No storage, no new fetch.** nav-items.js is pure data, and the reuse
  memo lives in module memory only. thread-actions.js's focus restore
  touches no storage and calls no `api()`, so the logout wipe needs nothing
  new.
