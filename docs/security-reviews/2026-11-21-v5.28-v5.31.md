## M1 — MEDIUM — `$` patterns in member text spliced the shell into the head (FIXED)

- Where: `withPageHead` inserted the page head with
  `html.replace("</head>", tags + "</head>")` (api/seo.mjs:238 before the
  fix), and the worker inserted its stamp the same way (worker.mjs:164).
  With a STRING replacement, `String.prototype.replace` expands `$'` (the
  text after the match), `` $` `` (the text before it), `$&` (the match) and
  `$$`. `attributeEscape` and `jsonLdBlock` escape `& " < >` but not `$`.
- Trust boundary: any member who can post a public thread (thread title,
  description, og/twitter tags and JSON-LD headline all come from its first
  line), and staff through the saved branding name/tagline/footer.
- Failure scenario: a thread whose first line is `Price $' now` makes
  `/posts/<id>` serve the whole rest of the shell (body, scripts) inside the
  `<title>` and every `content="..."` attribute. The shell's own quotes close
  the attribute, so the head carries a broken copy of the page: 7 `</head>`
  in the served HTML instead of 1 (measured by the RED test). Share previews
  and search results show garbage, and the stamp's `</head>` search can land
  inside an attribute. The spliced text is the static shell, not attacker
  markup, and member text stays escaped, so no script runs (and the CSP
  `script-src 'self'` would block inline handlers anyway); the impact is
  head integrity, not XSS.
- Fix: both insertions use a function replacement (`() => tags + "</head>"`,
  `() => stamp + "</head>"`), which never expands patterns.
- Pinned (tests/wave533-security-review.test.mjs): `$' $\` $& $$` in a thread
  title and in the saved branding name come back literal in `<title>`,
  description, og:title, og:site_name, site-name and the JSON-LD headline,
  with exactly one `</head>` and no extra `<body`; a source pin keeps both
  calls on a function replacement.

## L1 — LOW — no written way to revoke a leaked AUTOMOD_KEY (FIXED)

- Where: the AutoMod API section of docs/admin-guide.md said how to set the
  key, not what to do when it leaks. Since v5.30.1 production runs with
  `AUTOMOD_ENABLED = "true"` (wrangler.toml).
- Blast radius of a leaked key: hide posts/replies and hand out bans of at
  most 24 h (api/automod.mjs:45, clamped at :235) to non-staff members
  (staff refused, :286), re-banning after each expiry, at the
  WRITE_RATE_LIMITER rate on one shared `write:automod` bucket (about 45 a
  minute). It can also read the queue: new public and hidden posts, lobby,
  wall, profile text and REPORTED DM threads only. It cannot shorten or lift
  a ban (`applyUserBan` refuses while any ban is active, api/bans.mjs:81),
  touch staff, read unreported DMs, or sign in.
- Fix: the guide now says: `wrangler secret delete AUTOMOD_KEY` (API back
  to 404) or `wrangler secret put AUTOMOD_KEY` with a fresh value (old key
  401), or flip `AUTOMOD_ENABLED`; then Restore/Unban from the desk's
  AutoMod page. Pinned by a doc test.

## O1 — MEDIUM — every counted page view is an unauthenticated D1 write (OWNER DECISION)

- Where: `scheduleCount` (api/analytics.mjs:127-138) writes on every 200 HTML
  GET that is not DNT/GPC/bot/prefetch: one upsert, plus a second when a
  foreign Referer is sent. No rate limit applies to page loads.
- Failure scenario: a script with a browser User-Agent requests `/` in a
  loop. Each request costs 1-2 D1 writes (and the referrer insert counts up
  to 200 rows). On a plan with a daily write quota, exhausting it stops every
  forum write (posts, sign-ins) until the reset, and the totals on the desk
  are inflated. The writes ride `waitUntil`, so pages stay fast; the risk is
  cost and availability, not data exposure.
- Options (behaviour changes, so not made here): (a) gate counting with the
  existing READ_RATE_LIMITER keyed by the hashed IP — skip the count, never
  the page — which stores no IP and keeps the "no personal data" promise;
  (b) count only every Nth view per isolate and scale; (c) accept, relying on
  Cloudflare's DDoS layer, a paid D1 plan and the `ANALYTICS_ENABLED`
  kill switch.

## A1 — LOW — D1 reads per HTML load (ACCEPTED)

- `/posts/<id>` now costs, per load: the branding read (pre-existing), a
  session read when a cookie is sent, the post row, `canViewPost`'s ancestor
  ban/block checks and the reply-count rollup; `/users/<name>` one indexed
  read plus a block check. All bound, all `LIMIT 1`, all on indexed keys;
  a failure degrades to the generic head (api/seo.mjs:157-160). Reads are
  cheap and there is no per-request write. Accepted, but it sits with O1:
  page loads are the one unmetered path.

## A2 — LOW — the staff analytics GET also deletes (ACCEPTED)

- `readAnalytics` runs the retention DELETEs before reading
  (api/analytics.mjs:165). A GET with a side effect could be triggered
  cross-site: the session cookie is `SameSite=Lax`, so a top-level
  navigation by a signed-in admin would carry it. The only effect is the
  documented 90-day retention, in two bounded batches
  (`RETENTION_DELETE_LIMIT` 500, bound), idempotent and data-reducing; no
  data can be added, changed or read cross-site. Accepted.

## A3 — LOW — junk referrer hosts (ACCEPTED)

- Anyone can send any `Referer`, so up to `REFERRER_HOST_CAP` (200) junk
  host names a day can land on the desk's Visits page. They are hosts only
  (`^[a-z0-9.-]+$`, at most 253 chars), and the desk paints them with
  `textContent`, never as links (public/js/desk/visits.js:59). Accepted.

## Checks that passed

- **Analytics staff gate.** `requireStaff(request, env, false)`
  (api/analytics.mjs:162): anon 401, member 403, staff 200 (pinned in
  tests/wave530-analytics.test.mjs). No counting API exists; `days` is 7 or
  30 from a fixed map.
- **Referrer host parsing.** `new URL()` then `hostname`: userinfo, port,
  path, query and fragment drop out; IDN arrives as punycode (`xn--`), which
  `HOST_PATTERN` accepts; IPv6 (`[...]`) fails `HOST_PATTERN` and is
  dropped; hosts over 253 chars are dropped; non-http(s) is dropped; our own
  host and SITE_ORIGIN are dropped (api/analytics.mjs:76-91). Pinned in
  wave 5.33. An IPv4 referrer is the referring SITE's address, not the
  visitor's.
- **Skips.** Off unless `ANALYTICS_ENABLED === "true"`; GET only; prefetch/
  prerender, `DNT: 1`, `Sec-GPC: 1`, empty or bot UAs, non-200 and non-HTML
  responses and unknown routes are never counted (api/analytics.mjs:94-103).
  The UA list is a privacy floor, not a security control.
- **Error handling.** Planning and writing never throw into the page; a
  failed write is logged with `console.error`, not silently dropped
  (api/analytics.mjs:132-136). Pinned.
- **Binds and LIMITs.** Upsert 2 binds, referrer insert 6, retention 2 each,
  reads 2 each — all far under `D1_MAX_BOUND_PARAMS`; every read has a bound
  `LIMIT` (`days + 1`, `TOP_LIMIT` 20).
- **Row growth.** `route` is a name from the client router's fixed set,
  sliced to 32 chars (api/analytics.mjs:100-102), so page rows are at most
  (routes × days). The referrer cap is one `INSERT ... SELECT ... WHERE`
  statement; D1 runs statements one at a time, so concurrent views cannot
  race past 200. Retention bounds the table to about 90 days.
- **Migration 0063.** CREATE TABLE IF NOT EXISTS only; no IP, member id, UA,
  cookie or URL column (pinned in wave 5.30).
- **Desk Visits page.** `createElement`/`textContent` only, no storage, the
  server gate is the real one (pinned in wave 5.30).
- **AutoMod key compare.** SHA-256 of both sides, then a full 32-byte XOR
  sweep (api/automod.mjs:65-75); the bearer is 1-512 printable chars
  (:52); no key or `AUTOMOD_ENABLED !== "true"` answers 404 (:60-63, :335).
  Failed keys are not rate limited, which is fine for an owner-generated
  random secret. Pinned in wave 5.18 and 5.33.
- **AutoMod limits.** Queue: `read` limiter, `limit` 1-50, anchored cursor
  regex. Action: `write` limiter, the shared JSON size cap (`readJson`),
  `reason` ≤ 480 chars, ban reason passed through the word filter, ids safe
  integers, bound params only.
- **AutoMod ban cap and staff immunity.** Clamp to 24 h (:235); staff
  targets 403 before any write (:286); the queue never lists staff (:58).
  Pinned in wave 5.18 and 5.33.
- **AutoMod replay/idempotency.** A repeated hide is a no-op
  (`hidePostsBatch` returns 0), a repeated ban while one is active is a 409
  turned into `already` (:263), a repeated report is guarded by
  `WHERE NOT EXISTS` (:273-276). A replayed request cannot do more than the
  original; there is no nonce, so a captured request can be replayed after a
  ban expires — the same reach as the key itself (L1).
- **Head regex anchors / multiple `</head>`.** `SHELL_TITLE` and
  `SHELL_DESCRIPTION` remove the first match only, and `</head>` is the
  first occurrence; the shell is a static, owner-controlled file whose head
  comes first. After M1, member text cannot add a `</head>` (escaped `<`).
- **Attribute escaping.** Every value goes through `attributeEscape`
  (`& " < >`); all attributes are double-quoted, so `'` needs no escape.
  Pinned in wave 5.31.
- **JSON-LD escaping.** `JSON.stringify`, then `< > &` and U+2028/2029 as
  `\uXXXX` (api/seo.mjs:76-81); a `</script>` body cannot close the block.
  Pinned in wave 5.31.
- **OG_IMAGE_URL.** Operator-set; only `http:`/`https:` after `new URL()`
  (which strips tab/CR/LF), else the forum's own card; the value is
  attribute-escaped (api/seo.mjs:85-96). `javascript:` and `data:` fall
  back. Pinned in wave 5.31.
- **Canonical host.** `siteOrigin` uses `SITE_ORIGIN` (set in production)
  and falls back to the request origin only when unset; a Worker only
  receives requests for its own routes, `*.workers.dev` is 301'd first, and
  the HTML is `no-store`, so a spoofed Host cannot be cached for others.
- **Cache / personalised head.** The head differs per viewer only for a
  block pair (generic head). Every HTML response is `Cache-Control:
  no-store` (worker.mjs:163), so no shared cache stores a personalised head.
- **Head visibility law.** Thread excerpts only when `canViewPost` passes
  for a non-staff viewer; profiles only without an active ban and without a
  block pair; hidden, banned, blocked, deleted and missing render the same
  generic noindexed head. Pinned in wave 5.31 and the v5.32 sweep.
- **gitleaks allowlist.** Five exact anchored values, `regexTarget =
  "secret"`, `useDefault = true`, no `paths`/`stopwords`/`commits`. The new
  entry is the public Ahrefs Web Analytics site key, meant to sit in page
  HTML. The wave 5.28 pin allows only letters, digits, `-` and
  backslash-escaped `+ / =`, so each entry still matches one string.
- **v5.29.0 client fixes.** Save as text and reply anchors now also skip
  `[data-filtered-out]` (closes the v5.28 L1 and I1); fixed attribute names
  and a fixed selector, no user input in a selector.
- **index.html owner edits.** The owner's web edits added and then removed
  third-party analytics scripts (dac0e00); what remains is one
  `ahrefs-site-verification` meta (a public token) and a blank line. No
  inline script, CSP unchanged.
